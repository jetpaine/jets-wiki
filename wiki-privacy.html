Making the Wiki Private

Research for a plan of attack · 5 Nov 2026

Summary What GitHub Pro changes How the template works What I tested Why only pages get encrypted Where the template falls short What a password page protects Options A possible plan Questions for you Sources

Summary

Pro plus a private repo hides the code but not the site. A password page on top hides the pages, but only the HTML pages. The template you found is a good starting point, but it's built for a single page. Used as-is, it would lock index.html and leave the rest of the wiki readable.

  • GitHub Pro lets a private repo publish a Pages site, but GitHub's docs say the site itself stays public. Only Enterprise Cloud organizations can limit who views a Pages site.
  • The template encrypts one page with StatiCrypt. Visitors type a password, and the page is decrypted in their browser.
  • StatiCrypt itself can encrypt every HTML page of a site in one run, and its "remember me" option carries across pages. I tested this on a copy of the wiki, and it worked.
  • Gap 1, other files: anything that isn't HTML (the JSON, SVG, XML and text downloads, the stylesheet) is published unencrypted. Anyone who knows or guesses its address can read it. Decided: the wiki won't publish separate files, so this gap goes away (below).
  • Gap 2, history: what was public before stays out there. Making the repo private stops new access, but it can't recall copies people already made.

My suggestion: use Pro and a private repo, and run StatiCrypt directly in a small workflow that encrypts every page on each publish. Keep all content inside the pages, with no separate files, as decided. The template's own workflow is the wrong shape for a multi-page wiki. The details are below.

What GitHub Pro changes, and what it doesn't

Today the repo is public on a free account, so both the source and the site are public. Here's what each step changes:

Who can see…Today (Free, public repo)Pro, private repoPro, private repo, plus passwords
The repo: files, commits, historyAnyoneOnly you (and anyone you add)Only you
The site's pagesAnyoneAnyone with the URLOnly people with the password
Non-HTML files on the site (JSON, SVG, XML, text, CSS)AnyoneAnyone with the URLAnyone with the URL, unless moved into the pages
Page addresses and file namesAnyoneAnyone with the URLVisible: a name like ai-diagrams.html hints at what's inside
  • Pages on private repos: available on Pro, Team and Enterprise. Free accounts only get Pages on public repos. That's why making the repo private on today's account would take the site down.
  • The site stays public: GitHub's docs say Pages sites "are publicly available on the internet, even if the repository for the site is private". Limiting who can view a site needs an organization on Enterprise Cloud, so it's not an option for a personal account.
  • Limits: sites can be up to 1 GB, with a soft bandwidth limit of 100 GB a month. This wiki is well under both.
  • Price: GitHub's docs don't list prices, and this session can't reach github.com/pricing, so I haven't verified the $4/month. Worth a look before you upgrade.
  • If Pro lapses: I couldn't confirm what happens to a private repo's site after a downgrade. Most likely it stops publishing until the repo is public again or Pro is restored. Worth checking before relying on it.

How the template works

a-nau/password-protected-website-template (MIT licence, last changed December 2024) is a one-page site with a GitHub Actions workflow. You write the page as main.html. On every push to main, the workflow:

  1. Installs StatiCrypt 3 and, on the first run, deletes the template's salt so your site gets its own.
  2. Inlines assets (embed.py): images, CSS and scripts that main.html links to are pasted into the page as base64, written out as index.html.
  3. Encrypts index.html with the password from a repo secret, DECRYPTION_PASSPHRASE, using its own login template (password_template.html).
  4. Commits the encrypted index.html back to main and force-pushes it.
  5. GitHub Pages publishes from main. _config.yml tells it to skip main.html, assets/ and embed.py, so only the encrypted page goes out.

Its README says to make the repo private, since main.html and the assets sit there unencrypted. It also has a disclaimer worth repeating: "do not assume this to be bullet proof. Do not share bank information or similar this way."

Why only pages get encrypted, and what we'll do about it

Decided (5 Nov): no separate files. The wiki is for reading, mostly on a phone, so it doesn't need downloadable JSON, SVG, XML or text. Everything will live inside the HTML pages, where StatiCrypt encrypts it.

Why StatiCrypt only encrypts HTML. GitHub Pages is a plain file server: it hands any file to anyone who asks for its URL, with no chance to ask for a password first. StatiCrypt gets around that by turning each page into a small HTML page that holds the encrypted content, a login form and a decryption script. Only an HTML page can carry its own login screen.

A request for hsm.json or an image gets the raw file, and no script runs. Encrypting those would only make them unreadable, so StatiCrypt copies them as they are. This applies to any password protection that works in the browser on static hosting, not just StatiCrypt. Gating every file needs a server in front (option D below).

One thing stays visible whatever we do: each page's address and file name, for example ai-diagrams.html. If even the names should give nothing away, pages can be given neutral names.

Where the template falls short for this wiki

  • One page only. Both workflows encrypt exactly one file and write it to index.html. ai-diagrams.html, this page, 404.html and any future topics would publish unencrypted. StatiCrypt can do all of them (tested above), but the workflow needs rewriting to use that.
  • Non-HTML files stay public. The AI page links to hsm.json, hsm.svg, the tree XML files and behavior-trees.txt. Their contents are already shown inside the page, so the simplest fix is to drop the separate files. Pages could also offer downloads generated in the browser after login.
  • It rewrites main on every push. The bot commits the encrypted page back and force-pushes. On a wiki where both of us push, that can overwrite a commit that lands at the same moment, and the history fills with "encrypted files" commits. A cleaner pattern is for the workflow to encrypt into a build folder and hand that straight to Pages (the "GitHub Actions" publishing source). That way main only holds the readable source.
  • Supply chain. It pushes with ad-m/github-push-action@master, a third-party action pinned to whatever master is that day and given write access. It also uses an older checkout action (@v3) and an unpinned container image. If we take ideas from it, I'd use GitHub's own actions, pinned to exact versions.
  • Inlined assets break relative links, as its README notes. The wiki's pages mostly carry their own styles already, so this matters less here.

What a password page protects, and what it doesn't

StatiCrypt encrypts each page with AES-256. The key comes from the password through 600,000 rounds of PBKDF2-SHA256, and decryption happens in the visitor's browser. Nothing checks the password on a server.

  • The password is the whole defence. The encrypted pages are public files, so anyone can download them and try passwords offline as fast as their hardware allows, with no lockout. StatiCrypt's README says to "use a long, unusual password" and recommends 16 or more characters. Four or five random words, or a password manager's random string, would do. The template's --short flag turns off the warning about short passwords. I'd leave the warning on.
  • One password for everyone. There are no accounts. Anyone who has it can pass it on, and the only way to revoke access is to change it and republish. A change also logs out everyone who used "remember me".
  • "Remember me" keeps a hashed copy of the password in the browser. It lasts until it expires (we choose the number of days) or until you log out with #staticrypt_logout. On a shared computer, skip it.
  • Share links are as good as the password. StatiCrypt can make a link that logs you in (…#staticrypt_pwd=…). Anyone with that link gets in.
  • Not protected:
    • Non-HTML files (above).
    • File names.
    • The fact that the site exists.
    • Anything that was ever public: the old Defender X pages and the AI page's files are in the public repo's history today. Making the repo private stops new access, but forks, clones, and archive copies such as the Wayback Machine may already have them.

For a personal wiki, that's a reasonable level of protection. Like the template's author, I wouldn't put passwords, keys or anything financial behind it.

A possible plan (option C)

Not started. This is a starting point for the plan we put together.

  1. Prepare the repo while it's still public: add the workflow and a themed login page, with the old publishing left in place so nothing changes yet.
    • The workflow, on each push to main, checks out the repo, runs staticrypt over all pages into a build folder, and publishes that folder with GitHub's Pages actions.
    • The salt lives in a committed .staticrypt.json, so "remember me" survives each publish.
  2. Make every page self-contained (decided): put the state-machine SVG inside the AI page, then delete the ai-diagrams/ folder and its download links. Add a check to the workflow that fails the publish if anything other than HTML and style.css would go out.
  3. Upgrade to Pro and make jets-wiki private. Check that the site still publishes.
  4. Add the password as a repo secret. Switch the Pages source from "Deploy from a branch" to "GitHub Actions" so the workflow takes over. Push, and test every page from a private browser window.
  5. Decide about the old history: leave it (private from now on), or rewrite it. Rewriting history only helps if nobody copied it while it was public.
  6. Update the README with how to change the password and how to add a page.

Adding a topic later stays the same: write the page and push, and the workflow encrypts it on the way out.

Questions for you
