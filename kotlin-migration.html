Migrating from Kotlin to a Native Language

Defender X · Jesse Paine · 25 Oct 2026

TL;DR

Recommendation: don't migrate now, and if you ever do, don't pick C. The evidence in the repo says Defender X isn't held back by Kotlin today. Its measured costs are GPU shader work, which runs the same speed whatever language calls it.

  • The bottleneck isn't the language. The only recorded timings are screen effects: about 11 ms worst case with every effect on at 3584×1982, and ~6 ms of that is smooth bloom. That's fragment-shader time on the graphics card. A C port would make it 0% faster.
  • The hot CPU code is already written like C. The 6,000-particle effects system keeps its state in flat FloatArrays, the layout a C programmer would choose. On that kind of code the JVM's JIT typically lands within 1.0–1.5× of C.
  • Realistic gains from a native port: maybe 1.2–2× on CPU-heavy simulation loops, no GC hitches, instant startup, roughly 4–8× less memory, and a smaller download. None of these is a visible problem yet.
  • C is the wrong native language for a hands-off workflow. Nobody reads the PRs, and QA is playtesting. C's typical failures (use-after-free, buffer overruns, data races) are intermittent crashes and corruption that playtesting is worst at catching. If you go native, Rust fits your workflow better: its compiler catches those bugs instead of you.
  • The port would cost about 17,000 lines of game code, 5,400 lines of tests, and a rebuild of what libGDX does for you. It would also put the tuned feel of flight, AI and effects at risk, four months before Steam Next Fest (Feb 22, 2027).
  • The "extra cycles" ideas (hundreds of ships, 100k+ particles, live smoke, bigger AI) mostly come from moving work to the GPU and from better algorithms, which you can do in Kotlin now.

Next step: add a CPU stress benchmark next to the existing -PfxBench. If it shows the simulation can't hold 120 Hz at the scale you want, revisit a native port after Next Fest, starting with a one-subsystem Rust spike.

Why the question changes when nobody reads the code

You chose Kotlin because you could read and write it. That reason is weaker now: Claude writes the code, and you QA by playtesting. But the other side of the trade changes too. When nobody reviews the diff, the language's compiler and tests are the only reviewers left.

So the question isn't "which language is fastest". It's "which language gives the fastest game that an unsupervised agent can't quietly break". Three things matter more than raw speed:

  1. What the compiler refuses to build. Every bug class the compiler rejects is one that never reaches a playtest. Kotlin rejects null dereferences and memory corruption. C rejects neither.
  2. How bugs show up. A Kotlin bug usually means a wrong number or a stack trace that names the line. A C memory bug can be a crash ten minutes later in unrelated code, or a corrupted value that just looks like bad tuning. Playtesting finds the first kind well and the second kind badly.
  3. How well agents write it. Claude writes Kotlin, C, C++ and Rust well. In C, though, correctness depends on discipline that isn't enforced anywhere: ownership, lifetimes, bounds. Without human review, nothing checks that discipline.

There's also a deadline. notes.txt commits the demo to Steam Next Fest, Feb 22 to Mar 1, 2027, with a minimum of the dogfighting loop, the opening cinematic, enemy and wingman AI, and sound. Any migration competes with that list for the next four months.

What exists today

Defender X is 16,882 lines of Kotlin in 115 files, plus 5,425 lines of tests. It runs on the JVM (Java 21) with libGDX 1.11 over LWJGL 3.3.3 (GLFW + OpenGL + OpenAL), gdx-vfx 0.5.1 for screen effects, and JOML for math. The simulation steps at a fixed 120 Hz (SIM_TICK_SECONDS = 1/120) and draws to a 1920×1080 virtual canvas in 4.5 px macro-pixel cells (about 427×240 cells).

What the split shows: the game logic (AI, physics, most of the simulation) has no libGDX in it and would port mostly line by line. The libGDX-heavy half (render, fx, cinema, screens) is the half that needs a new foundation.

The libGDX surface in use is small and conventional: Gdx, Color, Matrix4, Vector2, MathUtils, ShapeRenderer, SpriteBatch, Texture, Pixmap/PixmapIO, FrameBuffer, ShaderProgram, OrthographicCamera, FitViewport, BitmapFont/GlyphLayout, Music/Sound, JsonReader, input keys and the LWJGL3 app launcher. No scene2d UI, no Box2D, no asset manager, no mobile backends.

Tooling that leans on the JVM:

  • aiDiagrams draws the enemy state machine by parsing the Kotlin source with the Kotlin compiler's own parser (kotlin-compiler-embeddable). It can't survive a language change as is.
  • The TUNING screen reads and rewrites GameConfig.kt as text with regexes. It would port, but it's tied to Kotlin syntax.
  • The behavior-tree ports use Kotlin reflection (KProperty1, KClass). C and Rust have no runtime reflection, so this becomes macros or generated code.
  • Gradle tasks (run, runScene, convertCinematic, shipFrames, btPalette, aiDiagrams) become CMake/Cargo commands or scripts.

Where the frame time actually goes

Nobody has measured the CPU side yet, and the GPU side is the only known cost. At 60 fps the budget is 16.7 ms a frame; at 120 Hz simulation, each tick must also fit in 8.3 ms.

What the repo records:

  • Screen effects (measured, -PfxBench): all effects on at 3584×1982, about 11 ms worst case; smooth bloom ~6 ms; each other effect ~1 ms. This is fragment-shader and framebuffer bandwidth on the GPU. It scales with pixel count, not language.
  • Vapor trails (observed): "a screen nearly covered in trails from 6 enemies showed no slowdown."
  • Scale today: 8 enemies (ENEMY_SPAWN_COUNT), 0 rocks, a 6,000-particle cap (EFFECT_MAX_PARTICLES).

What the code suggests would cost the most as the game grows. Each of these is an algorithm or architecture cost, so it hurts in C as much as in Kotlin:

Collision (CollisionSystem.detect)Every pair tested: n(n−1)/2, broad-phase circle then SAT8 ships = 28 pairs; 300 ships = 44,850 pairs per tick at 120 HzSpatial grid or sweep-and-prune broad phase

The pattern: the parts the language affects (raw loop speed, allocation) are not where the visible costs are. The part a language can't help with (O(n²) loops, CPU-side drawing, GPU fill) is where scaling would actually break.

Which language, if not Kotlin

Rust is the only native option whose compiler stands in for the code review you no longer do. C is the fastest to write badly. C++ sits between. Zig and Kotlin/Native don't fit this project.

Why not C, specifically. C is the language the original question named, so it deserves a direct answer:

  • No safety net. An off-by-one in the particle arrays writes into the next array. The game keeps running with a wrong value, which a playtest reads as "the smoke looks off", not as a bug.
  • More code for the same game. No generics, no lambdas, no RAII, no built-in strings or lists. The behavior trees, scene parser and tuning screen would each grow by perhaps 2–3× in lines, and every line is one nobody reads.
  • No speed edge over C++ or Rust. All three compile through LLVM or GCC to the same machine code for the same loops.

What you'd give up leaving Kotlin even for Rust: you can read Kotlin and step in when needed. Rust is harder to read cold, and compile times are longer (a 20k-line game builds in roughly 5–30 s incrementally, depending on dependencies).

Things outside libGDX that also have to be rebuilt:

  • The test suite, 5,425 lines of kotlin.test. Rust has built-in testing; C needs a framework such as Unity or Criterion; C++ has GoogleTest or Catch2.
  • Hot-reloading and the TUNING screen. TUNING edits GameConfig.kt's 1,249 lines of tunables as text. A native port should move tunables to a data file (TOML or similar) loaded at runtime, which is better anyway.
  • The aiDiagrams tool, which parses Kotlin with the Kotlin compiler. It would need a rewrite against the new language's parser (Rust: syn; C/C++: libclang), or the state machine would move to data that's drawn directly.
  • Behavior-tree port binding built on Kotlin reflection becomes macros (Rust) or code generation (C/C++).

What gets easier: distribution. Today a Steam build needs a bundled JRE (40–80 MB via jlink/jpackage) and -XstartOnFirstThread on macOS. A native build is one executable of a few MB plus assets.

What you'd lose for good: libGDX's path to Android, iOS and the web, if you ever wanted it. SDL3 and wgpu cover those too, though with more work.

How much faster it would actually be

Expect 1.2–2× on CPU simulation, 0× on GPU effects, and big wins only in startup, memory and download size. These are estimates from typical JVM-vs-native results on similar code, not measurements of this game. The benchmark in the last section would replace them with real numbers.

Where native code really pulls ahead is deliberate data-oriented and SIMD work: processing 4–8 particles per instruction, packing entity data into cache lines, and controlling memory layout precisely. That can mean 4–10× on specific hot loops. It isn't automatic, though. It needs code written for it, and the JVM's Vector API (incubating in Java 21) can do some of it in Kotlin too.

The honest frame: today's 8-ship dogfight probably uses a small slice of one CPU core for simulation. Making that slice 2× smaller changes nothing a player can see. Native speed matters only once you push scale by 10–100×, and at that point the algorithm fixes in the hot-spot table matter more than the language.

Two ideas are where native code truly earns its place: lots of AI ships thinking with lookahead every tick, and deterministic multiplayer. Both are post-demo features. Both are better served by a Rust rewrite of the simulation core only than by porting the whole game.

Risks, and what would be lost

The biggest risk isn't a missing feature. It's the tuned feel drifting during the port without anyone noticing. Months of tuning live in exact numbers and orderings ("Jesse's tuning: enemies take 9 hits once morale breaks").

Functionality that would be lost outright: none of the game's features. You'd lose libGDX's Android/iOS/web backends (unused today), Kotlin compiler-based tooling (rebuildable), and the JVM's crash stack traces with line numbers, which Rust panics keep but C segfaults don't.

How a migration would go, if the numbers call for it

Port incrementally, simulation first, with golden replays as the referee. Don't do a big-bang rewrite. Each phase ships a playable game, and each gate is a measurement, not a feeling.

Why incremental beats big-bang here. A full rewrite in one go is roughly 8–14 weeks of agent work with no playable build until the end. Then every difference in feel surfaces at once, with no way to tell which subsystem caused it. Porting the simulation behind a stable boundary lets you playtest after every step and stop at whichever phase is enough.

How to verify a port when nobody reads the code:

  1. Golden replays. Record seeded sessions with their inputs in Kotlin. The port must reproduce ship positions, hits and deaths within a small tolerance, tick for tick. This is the one test that protects feel.
  2. Port the tests first. The 5,425 lines of existing tests become the spec. The new code isn't done until they pass.
  3. Side-by-side builds. Keep the Kotlin build runnable during the port so a playtest can switch between them on the same seed.
  4. Sanitizers or Rust's checks in CI. In Rust, ban unsafe outside the FFI boundary. In C/C++, run every test under AddressSanitizer and UndefinedBehaviorSanitizer.

What about Phase 3? It's worth doing only if the Kotlin side becomes the problem: renderer CPU cost, the JRE in the Steam download, or startup time. Nothing today suggests it will.

The cheaper path: get the cycles in Kotlin first

Most of the headroom a port promises is available in days, not months, without changing language. Roughly in order of payoff per effort:

  1. Measure the CPU. Add a -PsimBench mode beside -PfxBench: spawn 10, 50, 100 and 300 enemies with a fixed seed and log ms per tick for AI, physics, collision, effects and drawing. Run JDK Flight Recorder or async-profiler once to see allocations. Effort: 1–2 days.
  2. Spatial grid for collision and sensing. Replaces the n(n−1)/2 pair loop. At 300 ships this cuts pair tests from 44,850 to a few thousand. 1–2 days.
  3. Draw effect cells on the GPU. Upload particle positions, colors and sizes once a frame and let an instanced shader draw the cells, instead of thousands of ShapeRenderer.rect calls. 2–4 days.
  4. Vapor grid on the GPU (issue #18, already planned). 2–4 days.
  5. Switch to ZGC (-XX:+UseZGC -XX:+ZGenerational) and remove the remaining per-tick allocations. Pauses drop below 1 ms. Half a day.
  6. Upgrade the stack: Kotlin 1.9.22 → 2.x (the K2 compiler builds faster), libGDX 1.11 → 1.13, gdx-vfx to its matching release. 1–2 days, plus re-checking effects.
  7. Package with jpackage and a trimmed jlink runtime for Steam: one launcher per OS, no Java install for players. 1 day.

If the benchmark later shows a CPU wall, there's a middle path before a full port: move only the simulation core (physics, collision, AI stepping) into a Rust library and call it from Kotlin through JNI or Java 21's Foreign Function API. The renderer, cinema, tools and menus stay in Kotlin. This is how many JVM projects adopt native speed, and it keeps most of the game's code and tooling.

Recommendation and next steps

Stay on Kotlin through Next Fest, measure the CPU, and decide on native code from numbers after the fest. If native wins, choose Rust and port the simulation core first. Don't choose C.

  • ☐ Add -PsimBench (enemy counts 10/50/100/300, ms per tick by subsystem) and record a baseline
  • ☐ Write down the scale target: how many ships, particles and AI agents the post-fest game should handle
  • ☐ Spatial grid for collision and sensing
  • ☐ GPU-instanced effect cells and vapor grid (issue #18)
  • ☐ ZGC and jpackage for the Steam build
  • ☐ Start recording golden replays of seeded sessions now. They protect tuning during any refactor, port or not
  • ☐ After Next Fest: rerun -PsimBench at the target scale. If a tick can't fit in 8.3 ms after the fixes above, start the Rust spike

Open questions:

  • What scale do you actually want? "BSG fleet battle" with hundreds of ships points toward native; a tight 8–20 ship dogfight doesn't.
  • Do you want multiplayer someday? Deterministic lockstep or rollback netcode is the strongest single argument for a native simulation core.
  • How much does reading the code yourself still matter? If you never want to step in, Kotlin's readability advantage counts for less.
